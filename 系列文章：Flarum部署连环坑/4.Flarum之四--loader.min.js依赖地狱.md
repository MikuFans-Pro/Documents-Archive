# Flarum 之四 - Flarum 部署后的连环坑之：loader.min.js 依赖地狱（最终章？）

> 导读：本文是「Flarum部署连环坑」系列的一部分。完整的问题梳理与解决方案总结，请参阅：[Flarum之八--20坑复盘与国内部署最小踩坑路径（最终章？）](https://lab.metazone.cc/d/13)

CDN 本地化之后又踩一坑。我当时心想这下能消停了吧，进帖子详情页一看，console 还是红的。

## 现象

坑全踩完、CDN 全切本地了，打开任意帖子详情页，控制台：

```
GET https://cdn.jsdelivr.net/gh/highlightjs/cdn-release@11.9.0/build/styles/github.min.css
net::ERR_CONNECTION_TIMED_OUT

GET https://cdn.jsdelivr.net/gh/highlightjs/cdn-release@11.9.0/build/highlight.min.js
net::ERR_CONNECTION_TIMED_OUT

GET https://cdn.jsdelivr.net/gh/highlightjs/cdn-release@11.9.0/build/languages/sql.min.js
net::ERR_CONNECTION_TIMED_OUT
```

不是 `loader.min.js` 加载失败——它已经从本地域名加载成功了。问题是 loader 加载完**之后**，它内部又去 jsdelivr 拉 `highlight.min.js`、`languages/*.js`、`styles/*.css`。

## 根因

`s9e/hljs-loader` 的工作方式是：

1. 页面加载时通过 `<script src>` 加载 `loader.min.js`
2. loader 初始化后，从 `data-hljs-url` 属性读取 base URL
3. 然后**动态创建**新的 `<script>` 和 `<link>` 标签，分别加载：
   - `{base}/highlight.min.js` — 核心库
   - `{base}/styles/{style}.min.css` — 主题
   - `{base}/languages/{lang}.min.js` — 语言文件

loader.min.js 里的关键代码：

```javascript
var A = document.currentScript,
    l = A.dataset,
    t = l.hljsUrl || "https://cdn.jsdelivr.net/gh/highlightjs/cdn-release@11.9.0/build/";
```

`t` 是 base URL，读 `data-hljs-url`，如果没设置就回退到 jsdelivr。

**问题出在哪**：s9e 在服务器端渲染代码块时生成的 `<script>` 标签上有 `data-hljs-url`，但你没法保证**所有地方**都正确设置了。比如有些模板遗漏了、缓存里是旧版、或者某些边缘路径根本没设。一旦 `data-hljs-url` 为空，loader 就直接走 jsdelivr。

更坑的是，之前修 CDN 的时候光想着"把 loader 拉到本地就完事"，压根没想过 loader **内部**还有个 jsdelivr fallback。你给一个组件做了本地化，结果它自己又拉了一堆子资源——子资源的加载逻辑里还藏着 jsdelivr 引用。套娃套到最后真想骂人。

## 修法：让 loader 自己推导路径

别去一个个修 s9e 模板的 `data-hljs-url` 了，绝对有漏的。直接**把 loader 里的 jsdelivr fallback 干掉**，让它从自己加载路径反推 base URL。

原代码：

```javascript
t = l.hljsUrl || "https://cdn.jsdelivr.net/gh/highlightjs/cdn-release@11.9.0/build/"
```

改为：

```javascript
t = l.hljsUrl || (function() {
  var s = document.currentScript.src;
  return s.substring(0, s.lastIndexOf("/") + 1);
})()
```

逻辑：
- 如果 `data-hljs-url` 有值 → 用它（兼容正常路径）
- 如果没有 → 从 `loader.min.js` 自己的 URL 推导：
  - `https://lab.metazone.cc/hljs/loader.min.js` → `https://lab.metazone.cc/hljs/`
  - `https://acg.metazone.cc/hljs/loader.min.js` → `https://acg.metazone.cc/hljs/`

这样不管 s9e 模板怎么变、有没有漏设 `data-hljs-url`，loader 都能从自己的来源自动定位到正确的资源目录。

## 涉及的层级

到这儿为止，jsdelivr 本地化其实涉及四层：

- **源文件**：`vendor/s9e/`、`vendor/flarum/emoji/` 里的 XSL 模板和 PHP 渲染器
- **编译缓存**：`storage/formatter/Renderer_*.php`，s9e 编译后的模板缓存
- **前端产物**：`public/assets/forum.js`，Flarum 打包后的 JS
- **静态资源**：`/var/www/hljs/loader.min.js`，loader 本身

每一层都能藏一个 jsdelivr，而且不是"或"的关系，是每一层都必须修干净：

1. 源文件漏了第 6 个 → 编译缓存跟着错
2. 源文件改了但缓存没清 → 运行的还是旧缓存
3. 上面的都对了但 forum.js 没重建 → 前端请求还走 jsdelivr
4. 前三层全对 → **loader 内部的 fallback URL** 又把 jsdelivr 复活了

## 修复步骤

```bash
# 1. 备份
sudo cp /var/www/hljs/loader.min.js /var/www/hljs/loader.min.js.bak

# 2. 替换 loader 里的 jsdelivr fallback 为自动推导
sudo sed -i 's#l.hljsUrl||"https://cdn.jsdelivr.net/gh/highlightjs/cdn-release@11.9.0/build/"#l.hljsUrl||(function(){var s=document.currentScript.src;return s.substring(0,s.lastIndexOf("/")+1)})()#g' /var/www/hljs/loader.min.js

# 3. 清所有缓存 + 重建 forum.js
sudo rm -rf storage/formatter/* storage/cache/* storage/views/*

# 4. Toggle 设置触发重建
UPDATE settings SET value = '1' WHERE key = 'theme_dark_mode';
# 访问站点
UPDATE settings SET value = '0' WHERE key = 'theme_dark_mode';

# 5. 四层验证
grep -r "cdn.jsdelivr.net" vendor/s9e/ vendor/flarum/emoji/ # 源文件
grep -r "cdn.jsdelivr.net" storage/ # 编译缓存
grep -r "cdn.jsdelivr.net" public/assets/ | grep -v "\.map" # 前端产物
grep -r "cdn.jsdelivr.net" /var/www/hljs/ # 静态资源
```

修完之后用 `grep` 搜 `loader.min.js`，里面再也没有 "jsdelivr" 了。高亮资源全部走自动推导的本地路径，不管 `data-hljs-url` 有没有设、设对没设对，都能跑。

现在回头看，jsdelivr 本地化真不是改几个 PHP 文件的事，整个是一棵依赖树：

```
emoji 显示 → flarum/emoji 的 JS 硬编码 URL
代码高亮 → s9e 的 3 个 PHP 文件 + 1 个 XML 模板
         → s9e 的编译缓存（藏得最深）
         → hljs-loader 内部的 fallback URL（终极隐藏坑）
```

每一层都不互斥，是叠乘——哪一层没修干净，jsdelivr 就从那个缺口复活。

## 更新：本地加载后又炸——hljs-loader 的竞态条件

fallback URL 修完后以为彻底消停了。第二天刷帖子详情页，控制台：

```
sql.min.js:17 Uncaught ReferenceError: hljs is not defined
 at sql.min.js:17:21
 at sql.min.js:17:53
```

语言文件执行时需要 `hljs` 全局变量（`hljs.registerLanguage(...)`），但 `hljs` 是 `highlight.min.js` 定义的。问题出在 loader 的加载逻辑里。

### 根因

看 `loader.min.js` 的 `p()` 和 `B()` 函数：

```javascript
function p(a) {
  for (let c of codeBlocks) {
    B(); // ① 异步加载 highlight.min.js
    // ... 判断语言 ...
    w[b]||(w[b]=1, r("languages/"+b, n)); // ② 立刻异步加载语言文件！
    e.hljs&&e.hljs.highlightElement(a) // ③ 检查 hljs 是否就绪
  }
}

function B() {
  if (!m) {
    m = !0;
    r("highlight", () => { // highlight.min.js onload
      y && e.hljs.configure(JSON.parse(y));
      n() // 重新扫描
    })
  }
}
```

问题在于步骤 ① 和 ② 之间：`B()` 一开始就发起了 highlight.min.js 的异步加载，但然后**不等待**就直接去加载语言文件了。而语言文件加载成功后执行时需要 `window.hljs` 存在。

在网络条件好的时候（比如走 CDN），highlight.min.js 可能先到——没问题。但本地加载时，如果 highlight.min.js 比语言文件大（121KB vs 几KB），语言文件可能先加载完毕，此时 `hljs` 还没定义，直接报错。

这就是竞态条件。修复需要：
1. 加一个 `L` flag 标记 highlight 是否加载完毕
2. 在语言文件 onload 里检查 `L`，如果 highlight 还没好就等待
3. 在 highlight onload 里设置 `L=!0`，然后触发等待中的语言文件

修复后的 loader 包装在补丁中，结构与 1.x 版本一致。本地加载后代码高亮完全稳定。

## 顺手记一下：XSLTProcessor 要被浏览器砍了

除了上面的问题，console 里还有个黄色警告，比 `[Violation]` 严重多了：

```
forum.js?v=67f3540f:336 [Deprecation] XSLTProcessor and XSLT Processing Instructions
have been deprecated by all browsers.
These features will be removed from this browser soon.
```

`XSLTProcessor` 是个老掉牙的浏览器 API，Flarum 的 forum.js（736KB）里调了它——s9e/text-formatter（2.14.3）在某些场景下要客户端跑 XSL 转换。Chrome、Firefox、Safari 三家已经联合决定干掉这个 API，不是什么单个浏览器的任性行为。

当前环境：Flarum 1.8.16 + s9e/text-formatter 2.14.3 + PHP 8.3.31。

现在只是警告，功能正常。但等浏览器真动手移除（问了一下AI，差不多 2026-2027），s9e 的实时预览、BBCode 渲染这些依赖客户端 XSL 的功能可能直接挂。

本地没法修——是 s9e 的底层问题，得等上游把 XSL 全部放服务端处理。s9e 作者在 Flarum 社区挺活跃的，大概率会在浏览器移除前出兼容版本。到时候 `composer update s9e/text-formatter` 就行，短期内不用太慌。
